## 根因一：alive 闭包恒 false（新增回归，阻塞）
`ssh.ts:139` `alive = () => tunnel?.exitCode === null && tunnel?.connected !== false`。`ChildProcess.connected` 是 **IPC 通道**标志，无 IPC 的 spawn 恒为 `false`（Node 24 与 Electron 主进程各实测：`connected=false exitCode=null`）。→ 首次 connect ECONNREFUSED 后 `alive()` 即 false → waitPort 立即返回 false → openRemote 抛 ERR 并杀隧道。正是任务 C 修掉的那个 bug 换了个门回来。
探针（假 ssh：connect 正常出行，隧道 600ms 后才 listen）：HEAD → `REJECTED after 313ms`；5a5df7db 版 → `RESOLVED after 1118ms`。

## 根因二：Sol ① 的修法仍有洞（派单人点的异步边界——成立）
`onTunnelGone` 在 `!firstUp` 时 `closed = true; throw`。throw 发生在 ChildProcess 事件回调里，**传不到 `await openRemote` 的调用者**，成 uncaughtException（Electron 主进程默认弹「A JavaScript error occurred」框）。更糟：它先把 `closed` 置 true，于是 `:141` 的 `if (!up && !closed)` 不进 → **openRemote 正常 resolve 一个死端口**，且之后永不重起。
探针（假 ssh：connect 出行后自删，隧道 spawn ENOENT）：`RESOLVED http://127.0.0.1:45889` + `uncaughtException: remote: invalid …`。
（隧道秒退 exit 255 的探针此次走了 alive→waitPort false 路径正常 reject——那是根因一的 alive 恒 false 碰巧掩盖；修好根因一后同样会落进 throw 路径。）
**谁把首起失败带给 await 的人**：只能是 waitPort 返回 false 后 `openRemote` 自己的 `throw`（在 async 函数里，会 reject）。事件回调里只该记标志，不该 throw、不该动 `closed`。
