## 分布与观察（实测，供 description 调词用，未改任何文案）
1. **不派工是「不愿」不是「看不见」**：30 个委派类组的主 bot 工具表全部
   （30/30）含 create_bot / send_to_bot / stop_bot（recorder 逐组记录），但
   全数据集只发生 2 次 create_bot 调用（都在 par1-two-tasks-2）、0 次
   send_to_bot、0 次 stop_bot。
2. **glm-5.3 对「自己顺手就能做」的文件任务一律自干**：single 12/12、
   attach/stop 回合0 12/12 全部直接用 bash/write/read/glob 完成（全数据集
   bash 35 / write 21 / read 15 / glob 14 次）。唯一触发委派的是明确说
   「这两件事可以同时弄」的 par1 措辞（1/6；同措辞 rep1/rep3 仍自干）。
3. **全链（唯一一次委派，par1-two-tasks-2）行为正确**：回合1 恰 2 次
   create_bot（todo / sum 两个 worker，均成功）→ 两个 worker 真实执行（bash
   审批自动放行）→ 两 end 合批成 1 条 pbots-worker 回报 → 污染回合内 2 次
   工具尝试（read 等）全部被 taint-guard 拒（工具成功 0）→ 末工具后恰 1 段
   转述 result → completed。编排机制本身在真模型下 E2E 成立。
4. **direct/chat 零误派**：24/24 组 0 协调者调用（含「好的谢谢」「早呀」），
   快问快答不派工也不问问题（唯一一次反问在 single2-2）。
5. stop 回合1 的口头停工（无 worker 可停时）：主 bot 全部以文字确认停止并
   说明「之前没做什么/顺手清理」（stop2-3 还删掉自己刚建的空 archive/），
   未幻觉调用 stop_bot——路由上计 FAIL（结构化 expect 要恰 1 次 stop），但
   行为对「没有在跑的 worker」是诚实的。
6. 每组明细与全帧：raw/<gid>.jsonl（主）+ raw/<gid>.w<k>.jsonl（worker，
   本批 2 件）；首行 d3o-meta（outcome/timeouts/worker 表/toolNames）。
   aux/ 存首跑 par1-two-tasks-1（2 worker、第二批回报被采集器截断——缺陷
   已修，该组已用修复后 harness 重采；截断件仅留诊断）。

## 结论
路由硬闸门（不误派、污染回合全拒、回报恰一次 result）全过；**委派倾向是
当前缺口**：create_bot description 的「user clearly wants a new task
delegated」在中文口语单任务/两回合场景下几乎从不成立。按 PLAN 约束，下一步
只调工具 description（P6-14b 开闸前的文案工作），不得看 prompts.json 调平。
