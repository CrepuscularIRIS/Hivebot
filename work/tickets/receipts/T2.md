## 5. 风险与存疑

1. **对工单配置的一处证据驱动偏离**：`AllowTcpForwarding no` 会让 sshd 拒绝 dsh-ssh 的流转发（`Received request to connect to path …, but the request was denied.`，sshd.log 实证）。OpenSSH 9.6p1 源码链：`do_authenticated` 只在 `allow_tcp_forwarding` 含 FORWARD_LOCAL 时装配本地 connect 许可集（session.c `set_fwdpermit_from_authopts` + 方向级 admin 决定），`channel_connect_to_path`（direct-streamlocal 的实际连接）吃这个许可集，`allow_streamlocal_forwarding yes` 只放行 channel-open 不放行 connect。夹具改为 **`AllowTcpForwarding local`**（最小档：direct 连接方向放行，远端监听方向仍拒）。隔离评估：sshd 仅 127.0.0.1:随机端口 + 本轮一次性密钥 + authorized_keys 每轮重生成，持钥者只有测试自身，风险封闭在夹具内。上游对照：live.e2e.ts 用的部署环境未禁 tcp forwarding。
2. **PLAN §5 存疑 2 证实**：远端子进程 env 叠加在 helper 环境上——③ 的 `PBOTS_SSH_MARK` 未显式传给 spawn，却出现在子进程 stdout，即 helper 会话环境（ForceCommand/SetEnv 注入）向下继承。
3. **PLAN §5 存疑 3 证实**：npm 版 `dsh-ssh/lib/helper.js` 在 pnpm 严格布局下 peer 解析正常（realpath 进 .pnpm store，同机远端路径有效，ready+fs+subprocess+sandbox 全通）。
4. 端口竞态重试路径（起两遍 sshd 的分支）本轮没被真实触发（自由端口一次成功）；代码按工单保留一次重试。
5. ④ 的「外写被拒」以 `exitCode != 0` + 文件不存在判定，错误细节（bwrap/权限报错文本）未断言——不同 sandbox backend 文案不同，锁文案会脆。
6. 密钥内容未打印、未写入回执（§4 输出均无 key 字样）；夹具目录随 tmp-sweep 进程退出清扫。
