## 1. 额度到底花在哪

本会话（含压缩前，跨数日）共 459 个 agent + 主会话，累计**输入 6030M tokens，其中约 99% 是缓存读取**；输出只有几 M。

| 来源 | 请求数 | 输入 | 占比 |
|---|---:|---:|---:|
| 主会话（编排者） | 3731 | 1952M | **32.4%** |
| P5-H3 builder（一个测试基建任务） | 2028 | 390M | 6.5% |
| 其余 457 个 agent | — | ~3690M | ~61% |

**结论：钱不是花在「写代码」上（输出 token 很少），而是花在「每次 API 请求都要把整段上下文重读一遍」。**
消耗 ≈ 请求次数 × 当时上下文大小。三个放大器：

1. **主会话上下文太大还被频繁唤醒**：上下文约 50 万 token，每次 cron tick（30 分钟一次，多数只写一行「零派发」）、每条 agent 通知都要整段重读一遍。
2. **长测试轮询**：agent 跑 e2e 全量时反复 pgrep / sleep / 看日志，每次都是一次完整请求。H3 一个任务 2028 次请求，大部分在等测试。
3. **流程倍数**：一个任务 = builder + verifier + 2 席 review + 复审 + 主会话记账，每个 agent 都要先读 LEARNINGS / PLAN / 报告，5 倍左右的重复阅读。

GLM 的 429 也是同一原因：并发 agent 多、每个都在高频请求。
