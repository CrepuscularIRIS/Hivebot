## 4. 锁语义（派单第 4 点）

读 launcher 第 64–76 行：锁冲突的分支（「双开」）**不看模式**，直接起 Electron（不带 handoff）然后 exit 0。trap 在锁之后（132 行）才装，所以冲突方不会误删对方的 serve.json（手测确认文件还在）。实际影响有两个方向：

- **A. serve 在跑时开桌面（`hivebot`）**：双开分支起的 Electron 找不到已有的 Electron 窗口，自己当上了主实例；没有 `PBOTS_DSH_HANDOFF`，main 就按「没配 dsh」起一个连不上 SDK 的空窗口（main/index.ts:219、ready.ts:33），15 秒后被启动器 TERM 掉（72–73 行）。用户看到的是窗口一闪而过、用不了。**定为已知限制可以接受**（serve 和桌面同机本来就互斥），但应该明确报错，不要弹一个注定被杀的窗口。
- **B. 桌面或另一个 serve 在跑时再起 `hivebot serve`**（这正是 Windows 侧 `ssh host hivebot serve` 的常见场景：用户 Ubuntu 上开着桌面）：手测结果 `rc2=0`、**没有状态行**；ui.log 里有 `Cannot find module '/tmp/bot-wt/T46c/serve'`——参数 `serve` 被当成 Chromium 参数透传给了 Electron，再被当成应用路径。也就是 ssh 会话里拉起了 Electron（DISPLAY 不在时恰好失败），而且退出码是 0，T46b 的客户端会误以为成功。这是 serve 路径的真问题，但不影响普通启动、不碰凭证；T46b 是它唯一的消费方，所以**不挡本单合并，挡 T46b 开工**。

附带小毛病：34/38 行 `echo "HIVEBOT-SERVE {"running":false}"` 引号嵌套，实际输出 `{running:false}` / `{stale:true}`，不是合法 JSON（走 stderr、退出码对，不挡）。

## 5. 安全面

- launch-token 只在 handoff 目录里：`mktemp -d` 建出来就是 700，token 文件 600（SDK 写的）。状态行、serve.json 里只有 handoff 路径，用真 token 值核过，0 次命中。
- 对端拿 token 要 `ssh host cat <handoff>/launch-token`，等于同一个 Unix 用户登录——和现有本机信任边界一样，**没有新增凭证面**。
- serve 模式不起 Electron，所以剥五键那段走不到；SDK 进程拿 key，和普通模式一样。
- 进程卫生：经理验收时发现两个施工期（23:40，cwd 已删的 `/tmp/bot-t46c-2v1qlp`、`-Fk7vgy`）遗留的 dsh（3463376、3467695），已 bot-reap。经理自己的几次运行都没留残留。规矩提醒：回执写了「stash 对照」——**多 worktree 期间禁 `git stash`**（CLAUDE.md §5），下次用 `git worktree add` 到基线 SHA 做对照。
